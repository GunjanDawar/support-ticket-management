# Support Ticket Management System Data Model Specification

## 1. Purpose and Scope

This document defines the logical persistent data model for the Support Ticket
Management System. It derives from the approved requirements in
`spec/requirements.md` and the boundaries and decisions in
`spec/architecture.md`.

This specification defines data structures, relationships, constraints,
mutability, and high-level database mapping. It does not add functional
requirements or define Java entities, SQL, migrations, repository
implementations, API payloads, the complete state-transition algorithm, or
database configuration.

## 2. Data Model Overview

The persistent model contains two entities:

1. **Ticket:** The aggregate record for a support request, including the
   fields users may update and its current lifecycle status.
2. **Comment:** A timestamped body associated with exactly one ticket.

No additional persistent entity is needed to satisfy the approved
requirements. In particular, assignee remains an optional String on Ticket;
it does not imply a User entity.

The relationship is:

`Ticket 1 → 0..* Comment`

The model supports:

- Ticket creation and durable identity.
- Updates to title, description, priority, and assignee.
- Storage of the current ticket status.
- Addition and retrieval of ticket comments.
- Case-insensitive partial search over title and description.
- Exact filtering by status.
- Durable storage in PostgreSQL and automated testing with H2.

Terminal-state restrictions and lifecycle transitions depend on current
persisted status, but authorization of those operations remains in the
service/business layer.

## 3. Ticket Entity

### 3.1 Logical fields

| Field | Logical type | Required | Meaning | Constraints | Mutability | References |
| --- | --- | --- | --- | --- | --- | --- |
| `id` | 64-bit integer identifier | Yes | Stable identity of the ticket | Primary key and unique; generated by persistence | Immutable after creation | BR-001; DM-002 |
| `title` | String | Yes | Short summary of the support request | Maximum 200 characters | Set at creation; ordinary PATCH for non-terminal tickets | FR-004; VR-002–VR-003; BR-018, BR-020 |
| `description` | String | Yes | Detailed description of the support request | Maximum 5,000 characters | Set at creation; ordinary PATCH for non-terminal tickets | FR-005; VR-004–VR-005; BR-018, BR-020 |
| `priority` | Priority value | Yes | Current urgency classification | One of `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` | Set at creation; ordinary PATCH for non-terminal tickets | FR-006; BR-003, BR-018, BR-020; VR-006 |
| `assignee` | String | No | Optional assignee value | Nullable; no additional format or length constraint is defined | Set or omitted at creation; ordinary PATCH for non-terminal tickets | FR-007; BR-004, BR-018, BR-020 |
| `status` | TicketStatus value | Yes | Current lifecycle state | One of the five approved statuses; initial value `OPEN` | Set to `OPEN` at creation; changed only by the dedicated transition operation | FR-012; BR-002, BR-009–BR-021; VR-008–VR-009 |

### 3.2 Identifier choice

BR-001 requires every ticket to have a unique identifier but does not prescribe
its type. This data model selects a persistence-generated 64-bit integer as the
Ticket identifier.

This is a **data-model choice**, not an assignment requirement. It provides a
compact, database-supported primary key and maps naturally to Java `Long` and
SQL `BIGINT`-equivalent types in PostgreSQL and H2. The API contract may choose
how identifiers are represented externally without exposing generation
details.

## 4. Comment Entity

### 4.1 Logical fields

| Field | Logical type | Required | Meaning | Constraints | Mutability | References |
| --- | --- | --- | --- | --- | --- | --- |
| `id` | 64-bit integer identifier | Yes | Stable identity of the persisted comment | Primary key and unique; generated by persistence | Immutable after creation | Data-model decision DM-002 |
| `ticketId` | Ticket identifier | Yes | Identifies the ticket that owns the comment | Foreign key to an existing Ticket | Immutable after creation | FR-008; BR-005, BR-019; PR-001 |
| `body` | String/text | Yes | Comment content | Must not be null; no maximum length is specified | Immutable after creation because comment editing is outside scope | BR-005; VR-007 |
| `timestamp` | Timestamp representing an instant | Yes | Time at which the comment was added | Assigned when the comment is created | Immutable after creation | BR-005; AC-006 |

### 4.2 Comment identity

A unique comment identifier is a **data-model choice** needed to address,
retrieve, and persist multiple comments reliably. The same generated 64-bit
integer strategy selected for Ticket is used for consistency and
PostgreSQL/H2 portability. No comment update or deletion capability is implied.

### 4.3 Ticket relationship

- A Ticket may have zero, one, or many Comments.
- A Comment belongs to exactly one Ticket.
- A persisted Comment cannot exist without its owning Ticket.
- The Comment holds the required foreign-key relationship to Ticket.
- A Comment cannot be moved from one Ticket to another.

The service layer must check the owning Ticket's status before inserting a
Comment. It rejects comment creation when the Ticket is `CLOSED` or
`CANCELLED`. The foreign key ensures ownership integrity, but it does not
enforce the terminal-state business rule.

No author field or User relationship is defined.

## 5. Enumerated Domain Values

### 5.1 TicketStatus

The only Ticket status values are:

- `OPEN`
- `IN_PROGRESS`
- `RESOLVED`
- `CLOSED`
- `CANCELLED`

The persisted value is required and constrained to this set. The database
constraint protects value validity; it does not decide whether a transition
between two valid values is allowed.

### 5.2 Priority

The only Priority values are:

- `LOW`
- `MEDIUM`
- `HIGH`
- `CRITICAL`

The persisted value is required and constrained to this set. No ordering or
numeric weighting is defined by this specification.

### 5.3 Representation choice

Status and Priority are stored using stable textual names rather than ordinal
positions. This is a **data-model choice** that keeps persisted meaning
readable and prevents enum reordering from changing stored meaning. The exact
physical column declaration is deferred to implementation and must remain
compatible with PostgreSQL and H2.

No additional status or priority value is allowed.

## 6. State-Related Data Constraints

The model distinguishes three concerns:

### 6.1 Data constraints

- Ticket status is required.
- Ticket status contains only an approved TicketStatus value.
- A newly persisted Ticket has `OPEN` as its initial status.
- The database stores the current status, not a status history.

### 6.2 Business rules

- Ordinary field updates do not change status.
- `CLOSED` and `CANCELLED` tickets do not permit title, description, priority,
  or assignee changes.
- `CLOSED` and `CANCELLED` tickets do not permit new Comments.
- A rejected operation leaves persisted state unchanged.

These rules are evaluated by the service layer using the current persisted
status.

### 6.3 State-machine rules

The only allowed transitions are:

- `OPEN → IN_PROGRESS`
- `IN_PROGRESS → RESOLVED`
- `RESOLVED → CLOSED`
- `OPEN → CANCELLED`
- `IN_PROGRESS → CANCELLED`

All other transitions, including same-status transitions, are invalid. The
service/business layer authorizes transitions and writes a new status only
after validation succeeds. The database schema does not encode the transition
graph or act as the primary transition validator.

## 7. Field Mutability

| Data element | Set during creation | Ordinary PATCH | Status-transition operation | Immutable after creation | Terminal-ticket behavior |
| --- | --- | --- | --- | --- | --- |
| Ticket `id` | Generated | No | No | Yes | Unchanged |
| Ticket `title` | Yes | Yes | No | No | Update prohibited |
| Ticket `description` | Yes | Yes | No | No | Update prohibited |
| Ticket `priority` | Yes | Yes | No | No | Update prohibited |
| Ticket `assignee` | Optional | Yes, including clearing it | No | No | Update prohibited |
| Ticket `status` | Set to `OPEN` | No | Yes | No | No outgoing transition from `CLOSED` or `CANCELLED` |
| Comment collection | Starts empty | Not part of ticket PATCH | No | Not applicable | New comment prohibited |
| Comment `id` | Generated | No | No | Yes | Unchanged |
| Comment `ticketId` | Yes | No | No | Yes | Unchanged |
| Comment `body` | Yes | No | No | Yes | New comment prohibited |
| Comment `timestamp` | Assigned | No | No | Yes | Unchanged |

Ordinary PATCH is limited to title, description, priority, and assignee.
Status changes use only the dedicated transition operation. Comment creation is
a separate operation and is not an ordinary Ticket PATCH.

## 9. Length and Validation Constraints

| Constraint | Backend validation | Persistence constraint | Notes |
| --- | --- | --- | --- |
| Title required | Yes | Non-null | Required by VR-002 |
| Title maximum 200 characters | Yes | Column capacity no greater than 200 characters | Required by VR-003 |
| Description required | Yes | Non-null | Required by VR-004 |
| Description maximum 5,000 characters | Yes | Column capacity sufficient for no more than 5,000 characters | Required by VR-005 |
| Priority approved value | Yes | Constrained to approved textual values | Required by BR-003 and VR-006 |
| Status approved value | Yes | Constrained to approved textual values | Supports BR-002 and BR-009–BR-016 |
| Comment body required | Yes | Non-null | Required by BR-005 and VR-007; no maximum length is specified |
| Comment timestamp required | Assigned and verified by backend | Non-null | Required by BR-005 |
| Comment ownership | Ticket existence verified as part of operation | Non-null foreign key | A persisted Comment requires an existing Ticket |

Backend validation produces the required API behavior and remains
authoritative. Database constraints protect persisted integrity if an invalid
write reaches the persistence boundary. Lifecycle transitions and
terminal-state restrictions are not duplicated as database transition logic.

## 10. Relationships and Referential Integrity

### 10.1 Cardinality

`Ticket 1 → 0..* Comment`

- The Ticket side is exactly one for every persisted Comment.
- The Comment side may be empty or contain multiple Comments for a Ticket.

### 10.2 Foreign key

The Comment table contains a non-null Ticket foreign key referencing the
Ticket primary key. This prevents an orphan Comment from being persisted and
supports retrieval of Comments for a Ticket.

### 10.3 Deletion

Ticket deletion and comment deletion are outside the approved scope.
Consequently, this data model does not define cascade, restrict, soft-delete,
or orphan-removal behavior for deletion. A future requirement that introduces
deletion must explicitly define its referential behavior before the model is
changed.

## 11. Timestamp Model

| Entity and field | Meaning | Required | Logical type | Mutability | Classification |
| --- | --- | --- | --- | --- | --- |
| Comment `timestamp` | Instant when the Comment was added | Yes | Instant representing when the Comment was added | Immutable | Requirement-driven by BR-005 |

The application shall treat the Comment timestamp as an instant on a common
timeline. UTC-consistent handling is preferred at application and persistence
boundaries to avoid server-local-time ambiguity.

The Ticket model does not include creation, update, transition, resolution,
closure, cancellation, or other lifecycle timestamps.

## 12. High-Level Database Mapping

No SQL is prescribed. The logical mapping is:

### 12.1 Ticket table

- One row per Ticket.
- Generated 64-bit integer primary key.
- Unique and non-null primary-key constraint.
- Non-null title with a 200-character maximum.
- Non-null description with a 5,000-character maximum.
- Non-null textual Priority value constrained to the four approved values.
- Nullable assignee text.
- Non-null textual TicketStatus value constrained to the five approved values.

### 12.2 Comment table

- One row per Comment.
- Generated 64-bit integer primary key.
- Unique and non-null primary-key constraint.
- Non-null foreign key to Ticket.
- Non-null comment body.
- Non-null immutable comment timestamp.

### 12.3 Important constraints

- Primary keys uniquely identify Ticket and Comment rows.
- Comment ownership uses referential integrity.
- Required logical fields are non-null.
- Status and Priority accept only approved values.
- The schema does not contain a transition matrix, transition-history table, or
  trigger that authorizes lifecycle changes.

Physical names, generation syntax, column types, constraint names, and
migration details are deferred to implementation design.

## 13. Indexing Strategy

Only indexes justified by approved access patterns are included:

| Index target | Purpose | Decision |
| --- | --- | --- |
| Ticket primary key | Ticket detail lookup and foreign-key target | Provided by the primary-key constraint |
| Comment primary key | Stable Comment identity | Provided by the primary-key constraint |
| Comment Ticket foreign key | Retrieve a Ticket's Comments and support relationship access | Add an index on the foreign-key column |
| Ticket status | Exact status filtering | Add a B-tree-compatible index on status |

Case-insensitive partial matching over title and description may use patterns
equivalent to `%keyword%`. A normal B-tree index does not generally accelerate
leading-wildcard matching. This specification therefore does not claim that a
standard title or description index satisfies BR-006.

The initial model does not require Elasticsearch, Redis, an external search
service, or a PostgreSQL-specific full-text or trigram index. The detailed
query implementation and any evidence-based search optimization are deferred
to query implementation and performance review. Any later PostgreSQL-specific
index must account for H2 test behavior rather than being assumed portable.

No index is introduced for sorting because sorting is outside scope.

## 14. PostgreSQL and H2 Compatibility

PostgreSQL is the application database and H2 is the automated-test database.
The logical model remains portable by:

- Using common relational primary keys and foreign keys.
- Using generated 64-bit integer identifiers supported by both databases.
- Storing enum meaning as stable text without requiring a
  PostgreSQL-specific enum type.
- Using ordinary nullability and length constraints.
- Representing timestamps consistently without relying on a
  PostgreSQL-only temporal feature.
- Avoiding database triggers for lifecycle validation.
- Keeping search correctness in the repository/service query behavior rather
  than depending on a PostgreSQL-only search extension.

PostgreSQL and H2 can differ in string matching, case handling, timestamp
mapping, generated-key behavior, and SQL dialect. Automated tests must not
silently assume that H2 proves every PostgreSQL-specific behavior. If a
PostgreSQL-specific search optimization is later selected, its production
behavior requires PostgreSQL-aware verification while H2 continues to satisfy
the approved automated-test constraint.

No database configuration is defined here.

## 15. Persistence and Integrity Rules

The persistent model shall maintain these invariants:

1. Every Ticket has a unique, non-null identifier after persistence.
2. Ticket title, description, priority, and status are non-null.
3. Ticket title does not exceed 200 characters.
4. Ticket description does not exceed 5,000 characters.
5. Ticket Priority contains only an approved value.
6. Ticket status contains only an approved value.
7. A new Ticket begins with status `OPEN`.
8. Every persisted Comment has a unique, non-null identifier.
9. Every persisted Comment belongs to an existing Ticket.
10. Every persisted Comment has a non-null body and timestamp.
11. A rejected status transition leaves the Ticket row and its associated
    persisted state unchanged.
12. Application data committed to PostgreSQL remains independent of the
    backend process and available after application restart using the same
    database.

The service layer remains responsible for lifecycle validity, same-status
rejection, terminal-ticket restrictions, and transaction coordination. Value,
nullability, and referential constraints in the database complement rather
than replace backend validation.

## 16. Data-Model Decision Log

### DM-001 — Two-entity persistent model

- **Decision:** Model Ticket and Comment as the only persistent entities.
- **Classification:** Requirement-driven.
- **Rationale:** Ticket capabilities and durable Comments require these
  entities; no approved requirement requires another entity.
- **References:** FR-001–FR-012, BR-001–BR-021; Architecture Sections 2 and 8.

### DM-002 — Generated 64-bit integer identifiers

- **Decision:** Use persistence-generated 64-bit integer identifiers for
  Ticket and Comment.
- **Classification:** Data-model choice.
- **Rationale:** Provides compact stable keys with direct PostgreSQL, H2, and
  Java support. Ticket uniqueness is required; Comment identity supports
  reliable persistence of multiple Comments.
- **References:** BR-001; Architecture Section 8 (Persistence Architecture).

### DM-003 — One-to-many Ticket/Comment relationship

- **Decision:** A Ticket has zero or many Comments; each Comment has exactly
  one Ticket through a required foreign key.
- **Classification:** Requirement-driven data-model decision.
- **Rationale:** Supports adding multiple Comments while preventing orphan
  Comments.
- **References:** FR-008, BR-005, BR-019, PR-001; Architecture Sections 3.3
  and 8.

### DM-004 — Textual status representation

- **Decision:** Persist status using stable textual names constrained to the
  five approved values.
- **Classification:** Data-model choice supporting requirements.
- **Rationale:** Preserves readable meaning and remains portable across
  PostgreSQL and H2 without encoding the transition algorithm.
- **References:** BR-002, BR-009–BR-017, VR-008; Architecture Sections 5 and
  8.

### DM-005 — Textual priority representation

- **Decision:** Persist priority using stable textual names constrained to the
  four approved values.
- **Classification:** Data-model choice supporting requirements.
- **Rationale:** Avoids ordinal coupling and enforces the approved value set.
- **References:** BR-003, VR-006.

### DM-007 — Comment deletion is out of scope

- **Decision:** The data model does not define comment deletion, soft
  deletion, or deletion metadata.
- **Classification:** Requirement-driven.
- **Rationale:** Comment deletion is not included in the approved
  requirements. The model therefore does not introduce deletion flags,
  deletion timestamps, or soft-delete behavior.
- **References:** Explicit Non-Goals; approved requirements scope.

### DM-008 — Minimal query indexes

- **Decision:** Use primary-key indexes, a Comment Ticket-foreign-key index,
  and a Ticket status index; defer specialized search indexing.
- **Classification:** Data-model choice.
- **Rationale:** Supports approved identifier, relationship, and exact-status
  access patterns without claiming B-tree support for leading-wildcard search
  or introducing external infrastructure.
- **References:** Ticket lookup FR-003; Comment relationship/access FR-008;
  search FR-009 and BR-006; status filtering FR-010 and BR-007; combined
  querying BR-008; Architecture Section 3.3.

### DM-009 — Portable relational constraints

- **Decision:** Prefer common relational types and constraints supported by
  PostgreSQL and H2.
- **Classification:** Architecture-driven.
- **Rationale:** PostgreSQL is required for application persistence and H2 for
  automated tests.
- **References:** PR-002, PR-003, TC-003; Architecture AD-004 and AD-005.

### DM-010 — Service-owned lifecycle enforcement

- **Decision:** Store current status but do not encode transition
  authorization in schema logic.
- **Classification:** Architecture-driven and requirement-supporting.
- **Rationale:** The approved architecture makes the backend business layer
  authoritative and requires rejected transitions to avoid persistence
  changes.
- **References:** BR-009–BR-017, PR-005; Architecture AD-002 and AD-007.

## 18. Unresolved Data-Model Questions

The following details remain intentionally unresolved because they are not
defined by the approved requirements:

- Exact physical table, column, key, and constraint names.
- Exact identifier generation mechanism and sequence configuration.
- Exact physical timestamp column mapping in PostgreSQL and H2.
- Whether comment retrieval has an ordering guarantee; no sorting requirement
  is approved.
- Whether whitespace-only required Strings are valid.
- The HTTP/API representation of identifiers and timestamps.
- Whether production search performance later justifies a
  PostgreSQL-specific index or search strategy.

These decisions must not add product capabilities and should be resolved in
the appropriate implementation or API/query design stage.

## 19. Explicit Non-Goals

This data model does not introduce entities or persistent fields for:

- Users.
- Authentication.
- Authorization.
- Roles.
- Notifications.
- Attachments.
- Audit history or transition history.
- Categories.
- SLA or due dates.
- Ticket deletion metadata.
- Comment authorship.
- Reporter or creator identity.

It also does not define ticket deletion, comment editing, or comment deletion
behavior. These remain outside the approved requirements.
